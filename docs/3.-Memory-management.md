# Memory management

AsyncMqttClient buffers outgoing messages in a queue. On sending data is copied to a raw TCP buffer. Received data is passed directly to the API.

## Outgoing messages

`publish` will queue your message and return a packet ID. It returns `0` if the message was dropped, and it's your responsability to resend it. There are two reasons a message is dropped (both logged at warning level):

1. **The queue is full.** Every queued message holds a heap copy of its topic and payload, so the queue is capped at `MQTT_MAX_QUEUE_BYTES` (8192 by default) to bound how far `publish` can outrun the TCP link. Override the build flag to change the default, or call `setMaxQueueSize(bytes)` at runtime. `queueSize()` returns the bytes currently queued.
2. **Not enough heap.** Even with room in the queue, the allocation itself has to succeed. A message is dropped unless the largest free heap block covers the message *plus* `MQTT_MIN_FREE_MEMORY` (4096 by default) of headroom for the rest of your sketch. This is a guard against heap consumed elsewhere — the queue cap above is what bounds this library's own usage.

Note `MQTT_MIN_FREE_MEMORY` is headroom required *in addition to* the message size, not an absolute floor: a 10 kB publish needs ~14 kB free, not 4 kB.

## Incoming messages

No incoming data is buffered by this library. Messages received by the TCP library is passed directly to the API. The max receive size is about 1460 bytes per call to your onMessage callback but the amount of data you can receive is unlimited. If you receive, say, a 300kB payload (such as an OTA payload), then your `onMessage` callback will be called about 200 times, with the according len, index and total parameters. Keep in mind the library will call your `onMessage` callbacks with the same topic buffer, so if you change the buffer on one call, the buffer will remain changed on subsequent calls.
